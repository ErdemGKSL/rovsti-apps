# Reality check: ARCHITECTURE-SPINE.md (Rovsti Phone)

Reviewer: read-only pass, 2026-10-27. Local sources checked: gpui-fusion d6c8412 (`gpui`, `gpui_android`, `gpui_wgpu`), `~/src/gpuiforge` (HEAD b79779f), workspace `Cargo.toml`/`Cargo.lock`, `crates/rovsti_android`. Android claims checked against developer.android.com / source.android.com / AOSP roles.xml where the fetch tool returned usable text. Where the fetch returned only navigation chrome, the claim is marked UNCONFIRMED rather than passed.

Legend: CONFIRMED (evidence found), PARTIAL, UNCONFIRMED (asserted, not verified), WRONG/RISK.

## Verdict

Mostly sound and unusually well grounded in the GPUI/GPUiForge side (all gpui and gpuiforge claims I could check were true). The Android side leans on training data in several places, and three items are factually risky as written: the `forIncomingCall` argument order, AD-17's `onError` override, and the APK path after eject. Nothing is fatal; all are cheap to fix or to bake into the S1/S2 spikes as explicit checks. Status "final" is premature for AD-2, AD-17, AD-20 until the items under "Must fix" are addressed.

## Top findings

1. **WRONG/RISK (AD-2): CallStyle argument order.** The spine says `forIncomingCall` takes "Answer, Decline PendingIntents". Both the platform and the NotificationCompat API take `(Person, declineIntent, answerIntent)`; the official CallStyle guide example passes `declineIntent, answerIntent`. Swapped intents would make the Answer button decline. Also not stated: a `Person` with a name is required, and the platform's rule about when CallStyle needs a foreground service or full-screen intent could not be confirmed (UNCONFIRMED, see below).
2. **WRONG/RISK (AD-17): "MainActivity overrides onError handling" is not possible with the shipped host.** `GpuiActivity` installs `session.setOnError` inside its own `onCreate`, `session` is `private lateinit`, and the handler calls `setContentView(TextView)`, replacing the whole surface. A subclass cannot override it. After eject the host module is user-owned, so it is achievable, but only by editing `GpuiActivity.kt` (or making `session` protected / adding an open `onGpuiError`). The spine must say that, and that a replaced content view must not drop the call notification (it will not; the notification is Kotlin-only, which is fine).
3. **RISK (AD-20): debug APK path.** The spine gives `apps/phone/target/gpuiforge/android/app/build/outputs/apk/debug/app-debug.apk`. That is the managed `project-dir` default. AD-19 ejects to `platforms/android` and switches to `management: manual` with `project-dir` recorded in `gpuiforge.json`; docs/usage.md says "keep the configured launch identifiers and artifact path in sync" in manual mode. After eject the APK lands under `apps/phone/platforms/android/app/build/outputs/apk/debug/`. Fix the path (and `check-apk.sh`).
4. **UNCONFIRMED (AD-1/AD-2/S2): full-screen intent on a sideloaded Xiaomi/HyperOS device.** AOSP fsi-limits confirms: Android 14 default-grants USE_FULL_SCREEN_INTENT; the Play Store revokes it for non-calling/alarm apps; `NotificationManager.canUseFullScreenIntent()` and `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` exist; OEMs decide qualifying apps. Without it the call degrades to a heads-up that persists about 60 s on a locked device (third-party source, not AOSP). The spine never mentions `canUseFullScreenIntent()` or a Setup Item for it, and nothing was found about HyperOS "display pop-up windows while running in the background" / lock-screen permissions. S2 mentions "HyperOS lock-screen behaviour" but there is no committed decision for the denied case (the likely fallback is heads-up with Answer/Decline, which AD-2 already supports; say so, and add `canUseFullScreenIntent()` to the Setup checklist, FR-5..8).
5. **RISK (AD-8/AD-5): `nativeOnEvent` before the library is loaded.** Confirmed from `gpui_android` that `main` runs once per session at the first non-zero Surface, `JNI_OnLoad` (generated in the app crate by the entry macro) loads at `System.loadLibrary` inside `GpuiActivity.onCreate`, and `nativeInit` is only reachable after that (matching AD-8 ordering). But `RovstiInCallService` can push `nativeOnEvent` in a cold process where the library has never loaded, which throws `UnsatisfiedLinkError`. AD-5 says "events with no sink are dropped" but that is the Rust side; Kotlin needs an explicit `nativeReady` flag set by `attachNative()` and reset never (library stays loaded for the process life). Not stated in the spine.

Further notable items (6-10) are below.

## Other findings (6-10)

6. **AD-20/S1 min_sdk method conflict** (see Stack notes): `gpuiforge.json` variable vs hand edit; pick the variable.
7. **AD-22 numbers**: `platform_draw_time` may include vsync/surface waits, so "CPU frame work under 4 ms" cannot be measured from it alone, and `renderer` stats are not available on Android. Add a plan for CPU-only timing (e.g. `build_time` only) and GPU-side timing via SurfaceFlinger/perfetto.
8. **AD-18 manifest**: the InCallService must also include the `android.telecom.InCallService` intent filter and omit `IN_CALL_SERVICE_CAR_MODE_UI` (roles.xml). `exported=true` plus `BIND_INCALL_SERVICE` permission is the normal pattern. The host `GpuiActivity` already sets `android:configChanges` etc. in the template manifest; keep when rewriting the manifest.
9. **AD-3 lock-screen mode**: relies on `keyguard_locked` in the snapshot; `KeyguardManager.isKeyguardLocked` returns false when the keyguard is "locked but showing over" in some secure-lock states and is device-dependent; test on HyperOS. Also the app is the default dialer with `SYSTEM_ALERT_WINDOW` app-op granted by the role; irrelevant to this but means overlay-based fallbacks are possible if FSI fails on HyperOS (a possible S2 contingency not mentioned).
10. **Back / task handling**: GPUI `handleSystemBack` falls through to `Activity.finish()`; if Back pressed on the in-call surface finishes the activity, the session closes (`onDestroy` -> `session.close()`), so the next incoming call is a cold start, contradicting AD-1's "keep the GPUI session warm". Override back to `moveTaskToBack(true)` for the root, always.
