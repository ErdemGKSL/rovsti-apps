# Review: ARCHITECTURE-SPINE.md (Rovsti Phone), rubric pass v0.2

Reviewed 2026-10-28. Scope: AD-23..AD-36, the "Amended 2026-10-28" notes on AD-2/3/4/6/9/10/11/14/18, the v0.2 build order and spike table, Consistency Conventions, Stack and Deferred. Judged against the good-spine checklist. Read-only: the spine was not edited.

Evidence read: the spine (all 470 lines), PRD v0.2 section 4.11 (FR-41..FR-73) and NFR-14..18, `CallRegistry.kt`, `crates/rovsti_core/src/wire.rs`, `crates/rovsti_ui/src/storage.rs`, `crates/rovsti_android/src/{lib,calls,providers,bridge}.rs`, shared Kotlin (`WireJson.kt`, `RovstiBridge.kt`), `NativeIncoming.kt`, `MainActivity.kt`, `docs/spikes/s2-incoming.md`, workspace and crate `Cargo.toml`, and `~/Android/Sdk/platforms/android-36.1/android.jar` (checked with `javap`).

## Verdict: PASS WITH FIXES

The v0.2 amendments are disciplined. Each new AD has Binds, Prevents and a Rule. Old ADs are amended in place with a pointer, not silently rewritten. The additive-wire policy, the single pending-op machine, the `Caps` constants, and the spike table with owner-phone procedures are the right shape. AD-21 (no visual cuts) is respected everywhere and is the standing rule for the new surfaces (AD-35).

It is not yet safe to hand to parallel units. Three rules contradict each other or the PRD, two rules are not implementable as written, and several Kotlin/Rust divergence points are still left to each side. Every fix below is small and can be made in the spine text.

## Findings (ranked)

### F1 HIGH. AD-36's "shipped default is the fallback" is contradicted by AD-23, AD-27 and AD-28
AD-36 says each spike has "a shipped default" and "the default build is already correct on the fallback path". The spike table's "Fallback shipped by default" column then disagrees with the ADs those spikes govern:

| Spike | AD says (default) | Table says (shipped default) |
| --- | --- | --- |
| S7 / AD-28 | `Caps.REJECT_PATH == TELECOM` | `REJECT_PATH = HANDOFF` |
| S6 / AD-27 | `Caps.BLOCK_GUARD` default false | `BLOCK_GUARD = true` |
| S3 / AD-23 | Endpoint list; legacy only on a runtime timeout | "Legacy type-only list" |

A unit reading AD-28 builds TELECOM; a unit reading the table builds HANDOFF. Worse, the TELECOM default can ship an unverified claim: AD-28 itself says the outcome "is a Telecom toast with no callback" and Rust shows "Sent" best effort. PRD FR-56 says the result "is never silent: the screen says Sent or Opened Messages". With S7 unproven, the default build can say "Sent" when nothing was sent. Pick one meaning of "default" for all three. Recommendation: the table is right in principle (unverified behaviour ships on the truthful path until the spike story flips the constant), so make AD-27/28/23 say so, or state explicitly which spikes ship optimistic and why that is safe. For S6, also say where `isBlocked(raw)` runs when `BLOCK_GUARD` is true: it is a ContentProvider/binder query inside `onCallAdded` on the main Looper, in front of the incoming notification, which collides with AD-2 (answerability) and NFR-2. It must run off the main thread after the notification is posted, or only on a cached set.

### F2 HIGH. AD-30 needs JSON in `rovsti_core`, which the spine forbids
AD-30 puts `PrefsV2`, `BackupFile` and `ImportPreview::from(text, &current)` in `rovsti_core::settings`, and in the same breath says "`rovsti_core` has no `serde_json`". Parsing and writing backup text (and validating `v` and `kind`, rejecting over 256 KB) needs `serde_json`; today it is only a dev-dependency of `rovsti_core`, and the Invariants line says core depends on nothing but serde and thiserror. Either (a) move `BackupFile` text I/O and `ImportPreview` to a crate that has `serde_json` (`rovsti_ui::storage` or the phone app both do) and keep only the typed structs in core, or (b) add `serde_json` as a normal dependency of core and amend the Invariants. Left as is, two units will resolve it differently. Related: the Invariants diagram omits the existing `rovsti_ui -> rovsti_core` edge (Cargo has it, and AD-22 and AD-30 both need it) while saying "allowed edges only". Add it. Also `rovsti_ui::storage` is shared by Messages and Stops; AD-30 puts Phone-specific `PrefsV1->V2` selection and `Probe` there. Say whether the generic part stays in `rovsti_ui` and the Phone schema lives in the app, otherwise NFR-13 (shared foundation stays app-agnostic) is weakened.

### F3 HIGH. T9 on the key-handler thread breaks NFR-18 and AD-21's CPU budget
NFR-18: "T9 search over 2,000 contacts completes within 8 ms off the UI thread". AD-33: "It runs on the key handler thread" with an 8 ms unit benchmark. AD-35 then lists "off the key handler and render path" only for the index build. 8 ms on the UI thread consumes a whole 120 Hz frame (8.3 ms) and breaks the AD-21 target of CPU frame work under 4 ms. The incremental narrowing makes the typical case far cheaper, but the rule as written permits the worst case on the UI thread, and a desktop unit benchmark (flaky, different CPU) proves nothing about the phone. Decide: run `t9()` on the background executor and apply the result when it arrives (stale results for an older digit string are dropped by a query counter), or keep it on the UI thread but assert a tighter budget (for example 2 ms for the incremental case) measured by an S-t9 scenario on the device, with the 8 ms desktop test marked non-gating.

### F4 MEDIUM-HIGH. "One snapshot applied per frame (highest seq)" can lose transitions the spine depends on
AD-35: at most one snapshot is applied per frame, the highest `seq`. AD-4 says `CallModel` stores the last snapshot and never infers. Several behaviours need intermediate snapshots: the `disconnected` state with `disconnect_cause` before the call is removed (the call-ended hold, missed/ended reason, ended moment), the endpoint added/removed diff for the arrival and loss moments (AD-23 says the list "yields the added/removed ids"), and Waiting card appear/disappear moments. Kotlin keeps a call in `Disconnected` only until `onCallRemoved`, which Telecom fires immediately after; if both snapshots land in one frame, the disconnected one is dropped and the foreground call vanishes with no hold and no cause. Rule fix: the reducer applies every snapshot in `seq` order (cheap), computes `SceneDiff` against the last applied one, and only the notify/render is once per frame; or `CallModel` keeps the last non-empty call as an explicit "ended" state with its cause. Also define equal-`seq` (a pull and a push of the same snapshot): AD-5 says only "ignores any lower".

### F5 MEDIUM. Native incoming fallback is not carried into v0.2 (AD-1, AD-17, AD-28, AD-29)
`NativeIncoming.kt` exists, is documented as "the same layout, labels, order and copy as `incoming.rs`", has a `CURTAIN_ENABLED` switch (off), and is used "always" as the error view when GPUI dies while a call rings (`MainActivity.showNativeFallback`). The spine does not mention it. Consequences:
- Deferred says "Curtain / native incoming fallback implementation: only if S2 fails". It is implemented; what is deferred is only the switch. Ratify what exists.
- AD-28/29 add Message, Silence, the reply sheet, gestures and a Waiting card to the Rust Incoming screen. Nothing says whether the native error view must follow ("same layout" is now false) or is declared the minimum (Answer, Decline, End, End all, waiting handled by notification actions). Without that rule, one unit extends it and another does not, and AD-17's "a GPUI failure never hides a live call" is unverified for a two-call state (the native view shows one call).
Add one sentence to AD-17: the native error view is deliberately the v0.1 minimum, plus how it behaves with two calls.

### F6 MEDIUM. Multi-call selection and the pending-op machine leave real divergence (AD-24, AD-25)
- Foreground is "first Active ... (lowest id)". During a Swap both calls can be momentarily Active/Holding, and the lowest id wins, so the primary block can flip back and forth until Telecom settles. The pending `Swap(toResume)` target should pin foreground while the op is live. Same for Add call: with A still Active and B Dialing, the rule shows A as primary and B as background, which hides the outgoing call state the user just started; say whether Dialing beats Active when a second call is placed from the app.
- "Completed by ... the existing 2 s timeout": the built `completePending()` answers the target on timeout. For `Swap` and `Merge` completion must mean "clear and report failure", not "answer". The rule needs the outcome per op type. Likewise "starting a new op first completes the old one" means an in-flight `AnswerReplacing` answers the waiting call immediately while the replaced call may still be disconnecting (this is what the code does today); say that is intended for all op types.
- `onDetailsChanged` (used by the built code to rebuild immediately) is in neither the coalesced list nor the immediate list of AD-23, so the coalescing window is ambiguous for exactly the callback that carries `caps`, `props` and connect time.

### F7 MEDIUM. PRD coverage gaps and one PRD contradiction
- **FR-53 vs AD-27.** FR-53 lists "the Incoming Call Screen" as a place to offer Block. AD-27 says "There is no Block on the ringing screen." Reasonable (and UX may agree), but it is a deviation from a bound FR that is not recorded as a decision or an open question. Add it to the accepted-defaults line or change the PRD.
- **FR-43, third bullet** ("Settings shows whether the handset reports hearing-aid compatibility") has no owner. Nothing in AD-23/30/34 names the API (`TelephonyManager.isHearingAidCompatibilitySupported` or `TelecomManager` equivalent), its permission, or the wire/settings field. Binds lists FR-43 but covers only the shortcuts.
- **FR-71 keypad tones "follow system".** AD-30 stores `keypad_tones: Option<bool>` and mirrors it to Kotlin, but never says where the system setting is read (`Settings.System.DTMF_TONE_WHEN_DIALING`) or by whom, so Rust and Kotlin will each read it.
- **FR-52** is covered (`props` hd/wifi, log `features`). **FR-62** is correctly deferred with a note that it needs its own AD. All other FR-41..FR-73 appear in a Binds line or the Capability map.

### F8 MEDIUM. Seam contract is not fully fixed (AD-5, AD-6, AD-25, AD-28, AD-31, Conventions)
- AD-6 amendment says the new commands follow the same rules, including Boolean results. AD-28 returns `sent|opened|rejected_only|stale`, AD-31 returns envelopes, AD-26/33 return JSON. The rule "every call command returns Boolean" is silently weakened. State the three return kinds: command (Boolean), outcome (short enum string), pull/write (envelope), and which helper in `bridge.rs` (`call_bool` / `call_string`) each uses.
- Naming. The Conventions say JNI names mirror Kotlin 1:1, and the built bridge names are `callAnswer`, `callRoute`, `callAnswerReplacing`. The spine's new names are mixed: `swap()`, `merge()`, `silenceRinger()`, `answerHolding`, `routeEndpoint(id)` in AD-6 but `callRouteEndpoint`, `callSilenceRinger`, `callRejectWithMessage`, `callSelectAccount` elsewhere. Publish one table of the complete new `RovstiBridge` surface (Kotlin name, Rust fn, args limited to String/Int/Boolean per `Arg`, return kind).
- AD-16 (no blocking JNI on the UI thread) is not restated for the new pulls: `phone_accounts`, `voicemail_info`, `emergency_numbers` and the `Blocklist` calls all cross binder/ContentProvider boundaries. Say they run on the background executor and what the UI shows until they land.
- Events with no sink are dropped and "attach re-pulls" (AD-5). `document_result` and `ringtone_result` cannot be re-pulled. If the activity is recreated while the picker is open, the result is lost. Specify a Kotlin pending-result slot delivered on attach.
- AD-30 mirror: `settingsSync(json)` "on attach and after every change" plus Kotlin writing `flip_supported` into the same SharedPreferences. State that sync merges keys, not replaces the store, or `flip_supported` is erased.
- Wire placement is inconsistent: AD-4 lists `ringer_silenced` among snapshot extensions, AD-24 and AD-29 put it per call; AD-25 says "the wire carries `pending`" and the F0 list says snapshot-level; `selecting_account`/`accounts` (AD-26) appear only in AD-26. One consolidated field table (snapshot-level vs per-call, optional or not) belongs in AD-4 or AD-10, and the existing `contact_id` per call (present in `wire.rs` and `CallInfo`) should be added to it.

### F9 MEDIUM. Ratification gaps against the existing code
- **File locations.** The layout lists `SnapshotJson.kt`, `CallLogQuery.kt`, `ContactsQuery.kt` under the phone directory. In the repo they live in the shared bridge (`WireJson.kt` holds `SnapshotJson`, `Focus`, `ProviderJson`; `CallLogQuery.kt`, `ContactsQuery.kt` are in `crates/rovsti_android/kotlin/...`). The Deferred item "Promoting contacts/call-log Kotlin to the shared bridge ... when Messages needs it" is already done.
- **`Focus.of` lives in the shared, app-agnostic bridge**, but AD-24 makes it Phone's multi-call selection (top-level only, `background_call_id`, `can_swap`). Decide: keep a generic `Focus` in shared and a Phone-owned selector in `dev.rovsti.phone`, or declare the selection shared. As written, the unit that edits it breaks the "rovsti_android is app-agnostic" claim.
- **AD-10 amendment** says both parsers reject a higher `v` and render the last good snapshot. `rovsti_core::call` does not check `v` today (grep found none). Name it as new work, with a golden fixture.
- **AD-3** says `addKeyguardLockedStateListener` "where available". `minSdk` is 34 and the method is in the 36.1 jar (API 33), so the "else receivers" branch is dead. The built code uses receivers only. Choose: ratify receivers (and delete the listener sentence) or adopt the listener.
- **Prefs.** `Prefs` is a flat struct in `rovsti_ui::storage`; the v1 reader silently swallows a corrupt file (`unwrap_or_default`). AD-30's `.corrupt` copy, `bak-v{n}` copy and `Probe` are all new, which is fine, but the spine should say the existing `Prefs` and its tests are replaced, not extended, and where `last_tab_or` goes.
- **Seam extras not in the spine's command lists:** `callIncomingFrame`, `perfLog`, `contactPhoto`, `localTimeInfo` exist in `RovstiBridge`/`providers.rs` and are not mentioned in AD-6/AD-9/AD-31 ("complete list"). The AD-31 list is about writes, so only `incomingFrame`/`perfLog` need an explicit "kept" mention.

### F10 LOW-MEDIUM. Structural dimensions not decided, deferred or raised as questions
- **UI navigation and overlay model.** The spine lists ~8 new Rust views (settings, route picker, reply sheet, SIM chooser, details, blocked, diagnostics, conference) but no rule for who owns the overlay/page stack, what Back does inside Settings or Details (AD-1 only fixes Back to `moveTaskToBack` at the root), which overlays must auto-close when call state changes (reply sheet after the caller hangs up, SIM chooser when the call is lost, route popover when calls end), and the precedence between the Waiting card, the route popover and a sheet. This is the most likely place two view units diverge.
- **Accessibility of custom gestures.** NFR-10 and FR-59 require labels; reorder drag (FR-64), swipe/drag answer (FR-59) and the Undo window (AD-27 mentions TalkBack 10 s but not how it detects TalkBack) have no accessible alternative decided. At least raise it as an open question.
- **AD-3 amendment race.** "Add call runs `requestDismissKeyguard` and opens its sheet only from the success callback" while the sheet's Favorites/Contacts segments "do not open" when `keyguard_locked`. The callback can fire before the `USER_PRESENT` receiver or listener clears `keyguard_locked` in the next snapshot, so the view rule would still say locked. Order the two: the callback sets a one-shot "unlocked by user" flag, or the sheet waits for the snapshot.
- **AD-2 amendment.** The "Message" notification action is an activity PendingIntent; on a secure lock screen it prompts to unlock unless `Notification.Action.Builder.setAuthenticationRequired(false)` is used (as Answer needs). Say it explicitly, since AD-3 says the reply sheet is a call surface that works while locked.
- **Strings.** Labels created in core or Rust ("Bluetooth device {n}", "Couldn't merge calls", reason texts) have no stated home (a single `strings` module vs inline). Not a blocker; a convention line prevents drift.

### F11 LOW. Deferred, stack and API facts
- **Deferred.** Nothing in Deferred lets two units diverge except: the missed-badge line is a decided rule filed under Deferred (move it), "Glass pass merging internals" (acceptable; AD-35 says every new surface ships plain glass and merges later, but state that views must not hard-code per-key glass counts), and the "Accepted UX defaults" line, which delegates to the UX doc and should list the FR-53 deviation (F7).
- **Stack table.** Values match the repo (AGP 9.2.1, Gradle 9.4.1, NDK 29.0.14206865 installed, compileSdk 36.1 jar present, jni 0.21.1 with 0.22.4 latest per `cargo info`, gpui rev d6c84124). It still has no verification date or source, and NDK 30.0.16248370 is also installed (say it is not used). The jni "revisit on a gpui-fusion bump" decision is clear. The AD-23/24/29 API levels are not in the Stack table (CallEndpoint 34, `silenceRinger` 23/29, `getUserSelectedOutgoingPhoneAccount` 29, `BLOCK_REASON` 29); add a single "API floor" row so a unit does not add a version check.
- **Verified against `android-36.1/android.jar`:** `InCallService.getCurrentCallEndpoint`, `requestCallEndpointChange`, `onAvailableCallEndpointsChanged`, `onCallEndpointChanged`, `onSilenceRinger`, `canAddCall`, `onCanAddCallChanged`; `TelecomManager.silenceRinger`, `getUserSelectedOutgoingPhoneAccount` (public), `getDefaultOutgoingPhoneAccount`; `Call.Details` capabilities `ADD_PARTICIPANT`, `SEPARATE_FROM_CONFERENCE`, `DISCONNECT_FROM_CONFERENCE`, `RESPOND_VIA_TEXT`, properties `HIGH_DEF_AUDIO`, `WIFI`, `NETWORK_IDENTIFIED_EMERGENCY_CALL`; `KeyguardManager.requestDismissKeyguard` and the locked-state listeners; `TelephonyManager.ACTION_SHOW_VOICEMAIL_NOTIFICATION`.
- **Needs care:** `TelephonyManager.getEmergencyNumberList()` returns `Map<Integer, List<EmergencyNumber>>`, not "digit strings" (AD-33); the flattening to digit strings is a step to name. The `Call.reject(true, text)` behaviour ("verified in AOSP `RespondViaSmsManager`") cites no branch or version and cannot be checked offline; S7 covers it. Permission requirements of `getUserSelectedOutgoingPhoneAccount` and `getEmergencyNumberList` (spine says READ_PHONE_STATE) are not provable from the jar; S5 and S10 will show them.
- **Diagnostics probes mutate real data** (S6 blocks a number, S11 creates and deletes a contact, S12 inserts and deletes call-log rows) from a release APK. Add one rule: probes touch only rows they created and marked, and never run without an explicit tap per probe.
